## 1. 错误码分类 → 处置策略（P0，最高价值）

这是对方最成熟的一块：把上游错误码**逐条映射到账号处置动作**，而且每条判据的**先后顺序**都有实测理由。
我们现在的 `gateway/inference.py:cooldown_for_error` 只有两档（限流 → 冷却；其余看 `status_code not in (429, 502, 503)` 决定是否轮转），
**会把「请求自身的问题」误判成「账号的问题」**。

### 1.1 完整的分类表（建议照此实现）

| 分类 | 触发判据 | 处置动作 |
|---|---|---|
| `ErrModelBlocked` | 400/404 + code **11102** | **(账号, 模型) 负缓存避让**，指数 TTL 6h→24h；切模型/切账号即可用 |
| `ErrHardCredit` | **402**；或 **429 + code 14018**；或非 429 带计费关键词 | 硬冷却至**次日 04:00**（等签到恢复） |
| `ErrSessionDead` | 401 + **12153** | **Disable**（session 失效需人工重登，软冷却救不活） |
| `ErrAccountFault` | **11140 "request illegal"** → **Disable**（账号被上游封禁，需重登）<br>**14017 trial not activated** → 软冷却（补完 register 可自愈，禁用会挡住自愈） | 分两种，见左 |
| `ErrSoftRate` | **429**（先于关键词判）；或非 429 带限流文案 | 软冷却，**优先对齐上游重置墙钟** |
| `ErrPromptTooLong` | 4xx + **11115** | **不罚号、不轮转**，透传上游原文（含真实 token 数） |
| `ErrImageInvalid` | 400 + **11135** | **不罚号、不轮转**，fail-fast 透传 |
| `ErrNotFound` | 404 | 固定 60s 短冷却，**不随限流退避**（偶发路径缺失不是限流信号） |
| `ErrServer` | ≥500 | 喂熔断计数器 |
| `ErrWafBlock` | **403 且 body 无业务信封**（无 `"code":` / `"msg":`） | 软冷却（**不 Disable**），基数 60s + 指数退避 + 抖动 |
| `ErrContentBlocked` | 400 + 审核文案 | **不罚号**，走降级重试 |
| `ErrBadParams` | 400 + 11101 / "Unmarshal chat params failed" | **不罚号，但仍轮转**（不同账号模型权限可能不同） |
| `ErrClient` | 其他 4xx | 只换号不罚；**连败 N 次临时出池** |

### 1.2 判据顺序（这部分比表本身更重要）

对方注释里写得很清楚，**每一步的先后都有实测依据**：

1. **11102 最先判** —— 语义最具体（"模型在后端不存在"）。若被更宽的 4xx 兜底归为 `ErrClient`，
   坏号会留在池内反复被选中。
2. **402** —— 真正的计费余额耗尽状态码，最严、最不可自愈。
3. **sessionDead（401 + 12153）** —— 先于 429。**判据是精确词，具体优先于宽泛**；
   误判为限流会让该死号留在池中反复被选中。
4. **accountFault** —— **必须先于 `status == 429`**：14017 常带 429 状态码，
   若落到 429 分支会被误归"限流"（限流可指数退避等自愈，账号级故障等不来）。
5. **429 + code 14018** —— 明确的积分耗尽，归硬冷却。**只认结构化业务码**，不靠文案猜。
6. **`status == 429`** —— **先于「余额不足」关键词判**。429 的 body 高频携带
   `quota exceeded` / `额度不足` 这类**跨计费与限流两界**的措辞；
   若关键词先判，会把限流误归硬冷却到次日 04:00，**白扔一个号约 12 小时**。
   状态码是比关键词更权威的信号。
7. **非 429 + 计费关键词** → 硬冷却。
8. **非 429 + 限流文案** → 软限流。
9. **11115** —— **先于 404 / 5xx / WAF / 内容策略 / 通用 4xx**。上下文超限是请求级问题；
   若落 404 兜底会误冷却账号，落 `ErrClient` 只会白换号。
10. **404 / ≥500**。
11. **WAF 403** —— **先于内容策略 / 参数错误 / 通用 4xx 兜底**。WAF 是空体/HTML，
    永远命中不了那些层的文案 marker，落到兜底的代价是「只换号不罚」→ 连环 403。
12. **11135** —— 图片格式无效，确定性请求级错误。
13. **内容策略 / 参数错误 / 通用 4xx** 兜底。

### 1.3 WAF 判定的具体口径

```python
def is_waf_blocked(status, body) -> bool:
    # 403 且 body 无业务信封（无 "code": / "msg": 字段）
    # HTML 拦截页、空体、纯文本都命中
    return status == 403 and ('"code":' not in body and '"msg":' not in body)
```

关键点：**带业务信封的 403 仍走正常分类链**（11140 request illegal / 11128 等），
只有"裸 403"才是 WAF 拦截。畸形 JSON 但含 `"msg":` 字样仍按业务响应保守处理 ——
**宁漏判 WAF，也不误罚业务 403**。

### 1.4 我们现在的实际后果

| 场景 | 我们现在的行为 | 应该的行为 |
|---|---|---|
| prompt 超上下文（11115） | 当账号故障 → **轮转一遍健康号**，还把好号打进冷却 | 不轮转，透传原文 |
| 图片无效（11135） | 同上 | 不轮转，fail-fast |
| 积分耗尽（402 / 429+14018） | 按普通失败处理 | 硬冷却至次日 04:00 |
| WAF 403 | 落"其他" → 只换号不罚 → **连环 403** | 软冷却 + 抖动退避 |
| 模型不存在（11102） | 换号，但**下次还会选中同一个坏号** | (账号,模型) 负缓存 |

## 2. 模型级限流独立冷却（P0）

- **对方**：code **6004**（该模型使用量超限）**只冷却触发调用的那个模型**，切其他模型立即可用；
  `/status` 透出 `rate_limited_models` 台账。
- **我们**：6004 被识别为限流（`errors.py:_RATE_MARKERS` 有 `"frequency limit"`），
  但冷却落在**账号**上 —— `pool.py` 里没有任何模型维度（`pick()` 只接受 `regions`）。
- **后果**：一个模型被限流 → **整个账号被打停**，其他模型明明可用。

## 3. 连接层加固（P1）

对方 `internal/upstream/transport.go` 的四件事，每件都有踩坑依据：

1. **真正禁 h2**：`ForceAttemptHTTP2=false` **不够** —— 必须设**空 `TLSNextProto`**，
   否则日志仍报 h2 timeout。（他们明确记了"这是陷阱"）
2. **建连与握手超时**：`DialContext` 10s 建连上限 + 15s keepalive 探测；TLS 握手超时；
   `IdleConnTimeout` 压到 3 分钟（不取更激进的 20s，因为那会与 keepalive 语义冲突）。
3. **失败连接主动清池** —— 光靠 `IdleConnTimeout` 过期不够，坏连接会留在空闲池里继续被复用。
4. 刻意**不**用 `DisableKeepAlives`（每请求 TLS 握手开销换来的收益不划算）。

**我们**：`net.py` 只统一了 `trust_env=False` 与代理，**没有**任何超时/连接池/keepalive 参数，
超时靠每次调用传 `timeout=`。→ 建议在 `net.client_kwargs()` 里集中补齐。

## 4. 单账号在途并发上限（P1）

- **对方**：`pool.max_in_flight`（默认 3），占满的号不参与选号；
  **global 域单独一档 `max_in_flight_global`（默认 2）** —— 理由：global 域 WAF 风控更紧，
  压低单号并发。
- **我们**：全局搜索 **没有任何信号量/并发控制**。
- **风险**：单账号被并发打爆 → 触发上游风控 → 反而更容易 403。

## 5. Retry-After 头族（P1）

对方的优先级链：**body 重置文案 > `Retry-After` 头 > 有界退避**。

头族候选（大小写不敏感）：
`Retry-After`（整数秒）→ `Retry-After-Ms`（整数毫秒）→ `X-Ratelimit-Reset`（epoch 秒或毫秒）。

两个细节值得抄：
- **非纯数字的值（如 HTTP-Date 格式）直接不解析** —— 宁缺毋滥，不臆造等待时长。
- **上限校验**：超过 2 小时视为上游异常值丢弃（与冷却封顶同量级）。

**我们**：只解析 body 里的「将在 …重置」墙钟。

## 6. 连败降权（P1）

- 对方：`ErrClient` / 传输层失败**连败 N 次** → 临时出池（"不知道原因的兜底"）。
- 与冷却的关系：**「知道原因的惩罚」与「不知道原因的兜底」并存，取更长者，不叠加**；
  带权威分类的错误**不喂连败**（防重复计罚）。
- **我们**：有 `failure_count`，但只参与打分权重 `1/(1+failure_count)`，**没有出池机制** ——
  一个持续报错的号只要额度高，仍可能被反复选中。

## 7. 临时停用 / 恢复 与 自动禁用分离（P2）

- 对方是**两个独立状态位**（`manual_disabled` / `disabled`），各自清除，**都清空才回池**。
- 理由：避免**运维意图被自动复活路径意外解除**（例如签到解冻把运维刚停用的号又放回池里）。
- 语义是「对话流量摘除」而非「账号冻结」：停用期间签到、token 保活、排程任务照常执行。
- **我们**：单一 `disabled_reason` 字段 —— 手动停用和自动禁用**共用一个位**，
  签到解冻这类自动路径可能把人工停用一并清掉。

## 8. 系统提示词三模式（P2）

`prompt.mode` 三档：

| 模式 | 行为 |
|---|---|
| `passthrough`（缺省） | 透传客户端原始 system；**遇内容拦截自动降级**为中性提示词重试 |
| `custom` | 网关用自有提示词**替换**客户端 system/developer（从源头消除模板句误报） |
| `append` | **两者并用** —— 在开头连续的 system/developer 块**之后插入**网关提示词，<br>客户端项目规范与网关人格共存；降级期退化为 `custom` 语义 |

**我们**：只有 `ensure_leading_system`（首条不是 system 就补一个空 system，防 11128 拒绝）。
`append` 模式对我们有实际价值 —— 既能保住客户端的项目规范，又能注入自己的内容。

### 逐项结论

#### ① 活跃地图领奖（连登档位兑换 + 抽奖）→ **吸收（已落地）**

**这是四项里唯一值得做的，而且它的价值不在"多拿积分"，在于它把我们已经做完的补签功能救活了。**

- 档位奖励（两区域一致）：7d → 积分 0 / 能量 2 / **补登卡 1** / 抽奖 1；
  14d → 50 / 3 / **1** / 1；28d → 150 / 5 / **1** / 1。**每档每月各可领一次**。
- **补签卡唯一的常规来源就是这里。** 实测两个账号 `makeup_cards.balance` 都是 0、
  `makeup_dates` 都是空 —— 也就是说 **补签卡从来没发过**，因为活跃连登还没到 7 天。
  → 补签功能不是坏了，是**没有弹药**。先领到档位奖励，补签才有意义。
- 旁证：redeem 被拒时上游的文案是「连续登录天数不足，**请继续打卡或使用补签卡**」——
  上游自己就把补签卡写成连登的补救手段，与"补签卡挂 growth 域"的结论一致。
- **成本极低**：`/activity/growth/streak` 我们**本来就在调**（`fetch_streak`），
  只需多解析一个 `redemption_status`；另外三个端点各十几行。
- **不需要伪造任何东西**：它的驱动是"每天有对话"，而**经过本网关的每一次对话都算**，
  连登是白送的。这跟开学季/夜猫子那种要伪造客户端事件上报的完全是两回事。

已落地：`billing.py`（`fetch_streak` 增 `redemption`、新增 `fetch_lottery_chances` /
`redeem_tier` / `draw_lottery`）、`scheduler.do_redeem`、`POST /admin/redeem`、
WebUI 连登弹窗里的档位列与领取按钮。**默认走演练，且没有做定时任务**
（档位是"每月每档一次"的事件，一个月最多 3 次，不值得加一条无人值守的写路径）。

#### ② 猫猫旅行 → **~~不吸收~~ 已改为吸收（2026-09-22 落地，见 AGENTS.md 第十四轮）**

- 国内版账号的猫**已经到站**：`state=arrived`、`record_id=7589803`、`reward_credit=10`、
  `daily_limit_reached=false` —— **有 10 积分躺在那里没人领**。
- 当初判"不吸收"的理由是：要做成闭环需要一套带状态机的每日排程，而收益只有
  10 积分/天/账号，性价比不划算。**这个判断基于一个错误的前提**（见下），已推翻。
- **前提纠正（2026-09-22 实测 `travel/config`）**：当时以为"每天能领 10 积分"，
  实际上 4 个地点（咖啡馆 / 商场店铺 / 健身房 / 古镇客栈）参数**完全相同**——
  时长 `1~4` 小时随机、奖励 `5~10` 积分随机，`daily_limit_reached` 决定**每天 1 趟**。
  所以真实收益是**每天 5~10 积分**，而"4 小时"是**单趟最长时长**、不是频率。
  成本侧也比当时估计的低：状态机只有 4 个状态，且**读是幂等的**，写可以严格串行。
- **用户明确要求接入**，且确实**只有国内版有**（国际版 `travel/config` 返回空 `data`，
  与参考实现的门控一致）→ 调度层按区域过滤，国际版零成本跳过。
- 落地内容：`billing.py` 5 个接口 + `scheduler.do_travel`（两阶段：只读并发 / 写串行）
  + `POST /admin/travel` + `/admin/streak` 带 `travel` + 设置页两个开关（默认关 + 演练）
  + 弹窗里的旅行区块。详见 `AGENTS.md` 第十四轮。
- ⚠️ 那条 `arrived` 记录（`record_id=7589803`）在 09-22 的两次探测之间**已经消失**
  （`claim` 全部返回 `400 no unclaimed travel`、状态变 `idle`、能量余额未变）——
  最可能是用户自己在官方客户端领掉了。所以 `claim` 的**成功分支至今未真机验证**。

#### ③ 开学季 → **不吸收**

- 国内版确实在活动中（窗口 `2026-09-13 ~ 2026-09-24`），但：
  1. **两天后就下线**（`end_at` 09-24 23:59），投入产出比极低；
  2. 主任务 `task_student_verify` 要**微信学生认证**，是人工步骤，我们既做不了也不该伪造；
  3. 其余任务要么是"分享给好友"（纯刷量），要么需要伪造 web 端事件上报
     （参考实现靠 `desktop_fingerprint` + `mini_chat_event` + `expert_actual_use_event` 造数据）；
  4. 国际版账号直接 401，本来就不适用。

#### ④ 夜猫子（`black_cat`）→ **不吸收**

- 国内版任务列表里确实有它：`accept_status=not_accepted`，要求
  「夜间 23 点–次日 8 点，新建对话并成功使用 GLM-5.2，每天 1 次，累计 3 天」。
- **但它的奖励是 `reward_credit=0` / `reward_energy=0` / `reward_buddy=true`** ——
  只给一个限定款 Buddy 盲盒，**不给积分**。
- 要完成就得在凌晨 1 点**伪造**一次 GLM-5.2 对话（参考实现正是这么做的：
  发 report 事件而不是真的发对话）。为一个纯外观奖励去伪造使用记录，不做。

### 顺带纠正/补充的两条

- **`/v2/activity/growth/tasks` 两区域的响应结构完全不同**（实测）：
  国内版是 `task_code` / `accept_status` / `progress{current,target}` / `reward_credit`（19 个任务）；
  国际版是 `code` / `status` / `level_name`，**没有奖励与进度字段**（5 个"养虾"任务）。
  按一个区域的字段名写解析，另一个区域会整列打成空 —— 探针脚本已两种都认。
- **`draw` 的两个 400 文案按区域不同**：国内版 `insufficient lottery chance balance`（没次数）、
  国际版 `lottery disabled`（**抽奖活动在国际版根本没开**）。判据要两个都认，
  只认一个的话另一个区域每次都会被刷成 WARN。
- **`redemption_status.remaining_days` 与 `streak.next_tier_remaining` 语义**：
  当时记为"未查清"（实测 3/5 与 4/2，跟"距下一档还差几天"对不上——国际版 days=3 差 4 天自洽，
  国内版 days=0 却是 2）。→ **2026-09-22 晚已查清**：
  `next_tier_remaining = 档位天数 − 当月最长连续段`，`remaining_days = 当月最长连续段`
  （**两者相加恒等于档位天数**：3+4=7 ✓、5+2=7 ✓）。
  **判档位仍是一律用 `streak.days` 与 `tiers[].days` 直接比**，那两个是自明的；
  这两个字段只是同一件事的两个视角，别当成两个独立信号。详见 `AGENTS.md` 第十四轮。

### 实施中偏离/补充的地方（供下次评估参考）
- **实施顺序**：P0 的错误分类表被前置为"先做"是对的——P1 的每一项（Retry-After、
  连败降权、fail_fast）都要挂在它的 `Action` 上，分开做会做两遍。
- **P1 的并发上限多了一条约束**：原评估只说"限制并发数"，实际必须明确
  **只覆盖「建连 → 首字节」窗口**——若覆盖整个请求生命周期，长回答的流式输出会互相饿死。
- **P2 的成本分层多了一条约束**：原评估只说"分三层选号"，实际必须让
  **tier0（实测免费）与 tier1（未测量）并列优先**，否则新账号永远拿不到实测数据、
  被永久饿死。这类"分层排序的边界条件"评估阶段最容易漏。
- **P0 的负缓存需要持久化**：原评估只说"负缓存"，实际必须落 DB（`model_blocks`），
  否则每次重启都会重新探测一遍已知不可用的 (账号,模型) 组合，白烧额度。
- **双状态位需要想清"谁能清哪个位"**：原评估只说"两个独立位"，实际的关键决策是
  **人工启用默认不清系统位**（否则用户点一下"启用"就把登录态已废的账号放回池子）。
