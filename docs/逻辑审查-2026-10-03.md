# Workbuddy2API 逻辑审查（2026-10-03）

**后续状态：六项已复现缺陷和两项性能风险已在 0.6.2 修复，详见 [发布说明](发布说明-0.6.2.md)。下文为修复前 0.6.1 的审查证据。**

审查基线为当时工作区 0.6.1。仅新增审查材料及 `.tmp` 下模拟验证脚本，未修改业务代码、生产数据库、部署或运行服务。所有复现均使用内存账号、模拟上游和临时数据库，不使用线上凭据、不发起收费请求。

现有回归：`python -m unittest discover -s tests`，528 个用例，13.475 秒，全部通过。下述缺陷不在现有用例的覆盖范围内；通过原有测试不能证明这些边界正确。

修复后的可重复行为验证见 [test_logic_regressions.py](../tests/test_logic_regressions.py)，本轮新增 22 项测试；原始临时复现脚本和 JSON 仅在本机保留，不随仓库发布。

## 已复现的问题

### 1. P1：未占用并发名额的请求会释放其他请求的名额

位置：[open_upstream_once](../workbuddy_one/gateway/inference.py)、[非流式 Chat](../workbuddy_one/routes/inference.py)、[acquire_slot](../workbuddy_one/pool.py)。

上限设置为 1，第一个请求仍等待首字节，第二个请求占位返回 False，但仍发送。第二个请求的 finally 无条件释放名额，导致计数从 1 变为 0，第一个请求实际上仍在连接中。后续选号据此误判该账号空闲。

当前代码明确把上限设计为软避让，所以“满载仍发送”本身是既有策略；**释放未获得的名额是确定的计数错误**。选号与占位分离还会让同批请求同时选择低价账号，实际避让效果弱于配置表现。

建议：先记录是否获得名额，只释放自己获得的名额；统一选号与占位的原子边界。满载处理应明确为有界等待或换号，保留现有“流式只计建立连接至首字节”的窗口。

### 2. P1：没有健康账号时，兜底重新选中积分耗尽或临时摘除的账号

位置：[pool.pick 兜底](../workbuddy_one/pool.py)、[pick_account](../workbuddy_one/gateway/inference.py)。

仅有一个账号时，将 credits_remaining 设为 0，pick_account 仍返回该账号；将 degrade_until 设为未来 600 秒，也仍被返回。正常候选经过 healthy 检查，但兜底只比较 cooldown_until；调用方也只拒绝冷却剩余超过 30 秒的账号。

影响：积分耗尽和连败摘除失效，系统继续碰撞已知不可用通道。

建议：兜底仍必须排除积分耗尽、系统禁用、模型负缓存和临时摘除；只对明确允许探测的短期冷却放宽。全部不可用时返回明确 503，避免持续重打。

### 3. P1：非流式 Chat 绕过统一换号重试

位置：[Chat 非流式分支](../workbuddy_one/routes/inference.py)。

账号 A 返回 429，账号 B 健康，stream=False 直接返回 429；统一 open_upstream 调用次数为 0。其他协议和流式 Chat 会进入统一连接、错误分类和换号流程。

影响：同样请求仅切换 stream 参数，就改变容错行为。低价账号暂时限流时，非流式客户端不会由另一可用账号接手。

建议：三协议统一共享上游连接与重试流程，非流式仅在输出阶段聚合；继续遵守请求级错误不换号、最多一次安全换号、已经输出内容不自动重试的边界。

### 4. P1：换号后的失败记错账号，传输错误还会重复惩罚原账号

位置：[open_upstream 换号分支](../workbuddy_one/gateway/inference.py)、[路由捕获错误](../workbuddy_one/routes/inference.py)。

复现：A 返回 429，转给 B，B 返回请求错误 400，最终记录的 account_uid 仍为 A。原因是 `(it, first, account) = await open_upstream(...)` 只有成功返回才赋值，异常时外层保留初始账号。

若 B 第二次发生 ConnectError，A 的 failure_count 为 2，B 为 1：A 已因第一次 429 冷却，路由随后又将 B 的连接错误施加到 A。这还可能把 A 原本按限流策略设置的较长冷却覆盖为较短的通用冷却。

建议：在异常/尝试结果中携带实际失败账号和错误策略是否已经执行；每次尝试只处置其对应账号一次。将一次客户端请求与其上游尝试记录关联，最终记录不依赖“仅成功才返回”的 account 变量。

### 5. P1：截断流在不同协议中有不同的完成判断

位置：[Chat 流式结束记账](../workbuddy_one/routes/inference.py)、[Anthropic finish](../workbuddy_one/adapters/anthropic.py)。

同一个模拟上游只返回一块 partial 文本，随后 EOF，没有 finish_reason 和 DONE：

| 协议/方式 | HTTP | 使用记录 | 完成语义 |
|---|---|---|---|
| Chat 流式 | 200 | ok | 没有正常结束标记，也没有错误事件 |
| Messages 非流式 | 200 | ok | 伪造 end_turn |
| Responses 非流式 | 502 | error | 正确拒绝截断结果 |

建议：把完成状态判定统一到共享层，明确区分正常完成、输出上限导致的未完成、上游截断和客户端取消。Messages 不应在缺少 finish_reason 时默认 stop；Chat 已发出 HTTP 200 后只能通过流内错误告知客户端。已经产生的文本和可用 usage 仍应保留用于记账。

### 6. P2：设置校验失败仍会保存部分字段

位置：[settings 保存](../workbuddy_one/routes/settings.py)、[末尾配置重载](../workbuddy_one/routes/settings.py)。

原签到时间为 9,21，同时提交签到时间 8 和非法额度刷新间隔 0，接口返回 400，但签到时间已经变为 8；config.load_overrides 没有执行。实现逐字段校验、逐字段提交，后面的错误无法撤销前面的写入。

影响：用户看到保存失败却已有部分配置变化；网络等运行时配置也可能出现数据库已变、内存配置尚未重载的状态。

建议：先验证并规整全部字段，再一次事务提交，提交成功后统一重载。并发保存也应保持同一批配置的一致性。

## 成本策略的取舍（已验证行为，不能直接认定为缺陷）

位置：[pool._prefer](../workbuddy_one/pool.py)。

当前严格先选最低目录报价，再在同价候选内看实测成本，符合上一轮明确采用的策略，但并不等于每次实际积分最少：

1. 国内目录价 1、实测收费；国际目录价 2、近期实测 credit=0，仍选国内收费账号。
2. 实测免费与尚无观测的账号处于同一优选层；未知账号积分即将到期时，可能先选未知账号而非已经确认免费的账号。

若目标进一步改为“优先消耗实际免费额度，再追求低价”，可让近期可靠免费观测先于目录价，未知成本仅进行有预算的探索。免费观测会受活动、缓存命中、积分四舍五入和输入输出比例影响，不能只凭一次 credit=0 永久判免费；需要观测新鲜度、样本数和收费后回退规则。

## 代码确认的性能风险（尚未做生产规模压测）

- [with_keepalive](../workbuddy_one/gateway/sse.py) 的 Queue 没有容量上限，后台 pump 可以持续读取上游。客户端慢时，待发送内容持续堆积；建议有界缓冲并完善取消、关闭上游及终态处理。
- [usage_content_stats](../workbuddy_one/db.py) 使用 fetchall 取出全部历史 input/output/reasoning 内容，再用 Python 求长度。包含完整 base64 图片的大库会有显著内存和扫描成本。建议用 SQL 聚合或增量维护统计，避免将所有原文同时搬进内存；不改变原文保留要求。

建议顺序：先修并发计数和账号健康兜底，再统一重试及错误归属、完成状态；随后处理设置原子性、成本策略和缓冲/统计开销。原审查阶段未实施；后续实现与部署结果以 0.6.2 发布说明为准。
